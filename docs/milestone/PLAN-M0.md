# PLAN-M0 — Benchmark Harness and Baseline

**Status:** phases 1-5 complete except the N-client stretch; results in `bench/RESULTS.md`
**Depends on:** nothing
**Blocks:** M1 (codec design targets), M1a (wire format cost decision)

---

## 1. Goal

A committed, re-runnable harness that measures Blink, Zap, ByteNet, and raw `RemoteEvent`
under identical load in Roblox Studio, and emits a results table with bandwidth, framerate,
drop rate, correctness, and per-packet allocation. netweave contributes **no library code**
in this milestone — only an empty mode slot the harness will pick up later.

When M0 is done we have numbers instead of opinions, and every later performance claim in
this project can be reproduced by running one script.

## 2. Why now

The research log ends with three open quantities that all later design work depends on:

- **How large is the codegen gap, really?** `§3.7-D` established that Blink's advantage is
  allocation coalescing, and `§3.9-V1` confirmed Zap does not coalesce at all. Whether a
  runtime schema can recover most of that is the central M1 hypothesis, and it is currently
  unmeasured.
- **What does a length prefix cost?** M1a must decide whether to spend 1–2 bytes per packet
  on a length field to get per-packet failure isolation (`§3.8-R`). That trade is only
  decidable against a measured byte baseline.
- **Where does allocation actually happen?** `§3.8-S` predicts decode-side table rehashing
  dominates, but nobody has measured it. `§3.7-L` notes Blink's own harness does not measure
  allocation at all.

Building the harness first also enforces the project's core discipline: the benchmark is the
only credible argument this library has (`CLAUDE.md §5`), so it ships before the library does.

### Schema families

Two, because the winner flips between them (`§3.9-Z`):

- **`ArrayHeavy`** — `Entity[100]`, six `u8` fields each. 600 B payload.
  Exercises allocation coalescing and per-element table construction. Blink is expected to win.
- **`FlagHeavy`** — 12 booleans, a 4-variant enum, a 2-variant enum, a `u16?` and a `u8?`.
  Exercises bit packing. Written **idiomatically per library** — see D-7. Measured sizes
  from `§3.9-AA`: Blink with `set` = 9 B, Blink with plain booleans = 19 B, Zap = 6 B.

## 5. Design decisions

**D-1. Fork Blink's harness methodology, not its plumbing.**
Blink's `benchmark/` already solved the hard measurement problems (`§3.7-L`): sample
`Stats.DataSendKbps` and real framerate rather than microbenchmarking serialization;
normalize bandwidth by observed framerate so a library that tanks FPS does not look
bandwidth-efficient; drain between modes with `while Stats.DataSendKbps > 0.5`; kill render
cost with `Camera.FieldOfView = 1` and CoreGui disabled; validate payload equality on the
receiving side. All of that is adopted.

Its plumbing is not. `download.luau` needs 7-Zip and a GitHub token, and `run.luau` requires
a human to press F5. We vendor deterministically and drive Studio over MCP instead.

**D-2. No `run-in-roblox`.**
Its role in Blink's harness is only: open place, inject script, pipe stdout back. The Roblox
Studio MCP (`start_stop_play`, `run_as_job`, `get_console_output`) covers all three and
removes the manual F5.

**D-3. Measure allocation with `collectgarbage("count")` deltas, on both sides.**
`§3.8-S` predicts decode-side table rehashing is the dominant hidden cost — every generated
decoder does `value = {}` followed by keyed assignment, which rehashes at 1→2→4→8 keys.
Blink's harness cannot see this.

~~We take a KB delta across N iterations with the collector stopped, and divide.~~
**Corrected during phase 2:** Roblox permits only `collectgarbage("count")` — the collector
cannot be stopped or forced. A collection landing inside a sample window shows up as a
negative or absurdly small delta. `Alloc.luau` therefore runs several windows, discards the
disturbed ones, and reports the median of the rest. The result is an order-of-magnitude
signal, not a precise byte count.

**D-4. Bytes-per-packet is derived, not measured directly.**
`normalizedKbps * 1000 / 8 / packetsPerSecond`. Cross-checked once per schema against the
byte counts already established in `§3.9-V3` (`boolean[8]` = 1 B on Zap, 8 B on Blink); if
the derivation disagrees with the known figures, the harness is wrong, not the libraries.

**D-5. Saturation load, not realistic load.**
1000 fires per `PostSimulation` frame for 10 s per mode, matching Blink's harness. This is
far past the 60 Hz guidance in `§2` on purpose — the goal is to separate the libraries, not
to model a game.

**D-6. Schemas are written once and compiled per mode.**
`bench/schemas/` holds the `.blink` and `.zap` sources plus the ByteNet and raw definitions
in Luau. A lune script regenerates all outputs. Hand-editing a generated file is a defect.

**D-7. Schemas are written the way each library's author would write them, plus a naive control.**
Blink has an explicit `set` type that packs flags into a bitfield, up to 32 per word
(`§3.9-AA`) — a Blink user writing `FlagHeavy` would use it. Benchmarking Blink with twelve
separate `boolean` fields would be a strawman. So `FlagHeavy` ships in two variants:

- **idiomatic** — `set` on Blink, plain booleans on Zap (which packs automatically), and
  the closest available construct on ByteNet and raw. This is the headline number.
- **naive** — plain booleans everywhere. Reported alongside as the cost of not knowing the
  library's escape hatch.

Reporting only one of these distorts the comparison in one direction or the other.

## 7. Acceptance criteria

1. `bench/RESULTS.md` exists and reports, for every (mode × schema × direction) cell:
   sent, received, drop rate, correctness pass/fail, normalized bandwidth percentiles
   (p0/p50/p90/p95/p100), framerate percentiles, derived bytes-per-packet, and allocation
   per packet split into encode and decode.
2. Every mode passes correctness on both schema families. A mode that fails validation is
   reported as failed rather than silently dropped from the table.
3. Derived bytes-per-packet for `FlagHeavy` reproduces the ratio already established in
   `§3.9-V3` — Zap materially below Blink on bit-packable fields — within measurement noise.
   If it does not, the harness is wrong.
4. The full matrix reruns from a clean checkout with two commands: regenerate schemas, then
   run the place. No GitHub token, no 7-Zip, no manual F5.
5. Every competitor version in the results table is pinned and matches `_refsrc/README.md`.
6. `selene` and `stylua --check` pass over `bench/`.

## 8. Risks

**R-1 — Studio loopback is not a network.**
`DataSendKbps` in Play mode measures the local replication path, not a real link. Mitigation:
state this in `RESULTS.md` itself, and never publish these numbers as absolute bandwidth.
Relative comparison is the only supported claim.

**R-2 — The allocation probe is noisy.**
`collectgarbage("count")` is coarse and the collector may run mid-sample. Mitigation: stop
the collector for the sampled window, use a large N, take a median across repeats, and treat
the number as an order-of-magnitude signal rather than a precise figure.

**R-3 — Adapter overhead pollutes the measurement.**
A uniform `fire(schema, payload)` interface adds an indirection each library does not
normally pay. Mitigation: bind the concrete function once outside the hot loop, exactly as
Blink's harness does (`Method = Event.Fire or Event.send`), so the loop body calls it
directly.

**R-4 — The harness measures the wrong thing and nobody notices.**
This is the expensive failure: every later decision would inherit the error. Mitigation is
acceptance criterion 3 — the harness must independently reproduce a byte ratio that was
already established by reading the generated code.

**R-5 — Studio automation over MCP proves unreliable.**
Mitigation: keep a manual fallback path (open the place, press F5, copy the JSON) documented
in `bench/README.md`. The harness must not depend on the automation to be correct, only to
be convenient.

## 9. Result

Run archived at `bench/runs/2026-09-03.json`, tables at `bench/RESULTS.md`, regenerated by
`lune run bench/report bench/runs/2026-09-03.json`.

**36 of 36 cells passed payload validation** across four modes, three schemas and three
directions (`Up`, `Down`, `FireAll`).

### Acceptance criteria

| # | Criterion | Outcome |
|---|---|---|
| 1 | Results report sent/received/drop/correctness/bandwidth/framerate/bytes/allocation per cell | **met** |
| 2 | Every mode passes correctness on both schema families | **met**, 36/36 |
| 3 | Derived bytes reproduce the ratios read out of the generated code | **met** — see below |
| 4 | Full matrix reruns from a clean checkout in two commands, no token, no 7-Zip, no manual F5 | **met** |
| 5 | Competitor versions pinned and matching `_refsrc/README.md` | **met** |
| 6 | `selene` and `stylua --check` pass over `bench/` | **met** |

Criterion 3 is the one that matters. The harness measured 601/601/603 B for `ArrayHeavy`,
10/7/20 B for `FlagIdiomatic` and 20/7/20 B for `FlagNaive` (Blink/Zap/ByteNet), reproducing
the counts derived by reading generated code in `§3.9-AA` — independently, at 10x the load,
through a completely different mechanism. Without this the rest of the table would be
unfalsifiable.

### What the run changed about this plan

- **D-4 was wrong.** Bytes derived from `Stats.DataSendKbps` reported 3.97 B for a 601 B
  payload — roughly 280x low — while measuring raw table traffic correctly. `Stats` does not
  account for buffer payloads in Studio. Replaced by `WireTap`, which sums `buffer.len` off
  each library's own remote.
- **D-3 was wrong.** Roblox permits only `collectgarbage("count")`; the collector cannot be
  stopped. Replaced by windowed medians that discard disturbed windows.
- **D-5 was wrong.** Blink's 1000 packets per frame assumes ~60 FPS. Studio runs uncapped at
  200-240 FPS, making that ~138 MB/s of offered load on `ArrayHeavy` — it measures the send
  queue. Lowered to 200.
- The client's server-side counters had to be snapshotted the instant a sampling window closes;
  reading them at the end of the run folded in everything that drained afterwards.

### Findings that feed M1

1. **Small payloads: raw `RemoteEvent` beats all three libraries on CPU** (239 vs 211-228 FPS on
   `FlagNaive`). Serialization does not pay for itself below some payload size. netweave should
   know where that crossover is rather than assume buffers always win.
2. **Batching is worth more than serialization.** Server to client on `ArrayHeavy`, `raw`
   delivered 11,138 of ~64,000 offered while every batching library delivered all of it, at the
   same payload size. ~6,400 remote invocations per second versus ~126.
3. **`table.clone(TEMPLATE)` works and is unclaimed.** ByteNet's `struct.read` does
   `table.clone(input)` and allocates 389 B/packet on decode against Blink's 641 and Zap's
   1474. `§3.8-S` proposed this from reading code; this run measures it, and it is the one axis
   where the runtime-schema library beats both code generators outright.
4. **Blink's allocation coalescing shows up in exactly one cell** — `ArrayHeavy`, 145 FPS versus
   125/124. On flag payloads it is behind. The advantage `§3.7-D` identified is real and narrow.
