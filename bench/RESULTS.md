## Read this before quoting any number

- **Studio play mode is loopback.** The replication path is real, the network is not. These
  results support relative comparison between libraries and nothing else. They are not
  bandwidth or latency figures.
- **Bytes per packet is exact**, counted by `WireTap` off each library's own remote
  (`buffer.len`), not derived from `Stats`. `raw` has no buffer to measure, so its byte column
  is empty rather than zero.
- **Allocation figures are order-of-magnitude only.** Roblox permits `collectgarbage("count")`
  but not stopping the collector, so windows it disturbed are discarded and the median of the
  rest is reported. The sample counts below say how much survived.
- Framerate is the p50 of one-second samples. Studio runs uncapped, so absolute values are much
  higher than a shipped game would see; only the ratios matter.

## Bytes on the wire

Includes the 1-byte packet id every library prefixes.

| Schema | Blink | Zap | ByteNet | raw |
|---|---|---|---|---|
| `ArrayHeavy` (100 x 6 x u8) | 601 | 601 | 603 | not measurable |
| `FlagIdiomatic` | **10** | **7** | 20 | not measurable |
| `FlagNaive` | 20 | **7** | 20 | not measurable |

This reproduces, independently and at 10x the load, the byte counts derived by reading the
generated code in RESEARCH §3.9-AA. That cross-check is PLAN-M0 acceptance criterion 3 and is
the reason to trust the rest of the table.

The Blink column is the entire point of the two flag variants: **the same schema costs 10 B or
20 B depending on whether the author knew about Blink's `set` type.** Zap packs automatically
and reaches 7 B either way. ByteNet has neither `set` nor an enum type, so both variants are
the same 20 B — that is what a ByteNet author can express, not a handicap imposed here.

## Framerate under load (client to server)

| Schema | Blink | Zap | ByteNet | raw |
|---|---|---|---|---|
| `ArrayHeavy` | **145** | 125 | 124 | **29** |
| `FlagIdiomatic` | 208 | 196 | 223 | **230** |
| `FlagNaive` | 211 | 226 | 228 | **239** |

**The winner flips between schema families, and one of the flips was not predicted.**

- On the 601 B array payload, Blink leads the buffer libraries by ~16%. That is where
  allocation coalescing (RESEARCH §3.7-D) shows up, and it is the only cell where it does.
- On small flag payloads **raw `RemoteEvent` beats all three libraries**. Serialization costs
  more than it saves when the payload is already tiny. No library in this space advertises
  that, and a game sending small structured messages at low rates is measurably better off
  with a plain remote.

## Delivery

| Cell | Offered | Delivered |
|---|---|---|
| raw `ArrayHeavy`, client to server | 58,200 | 58,178 |
| raw `ArrayHeavy`, server to client | ~64,000 | **11,138** |
| raw `ArrayHeavy`, `FireAll` | ~48,000 | **9,658** |
| every buffer library, every cell | offered | all of it |

**This is the measured case for batching.** At 200 packets per frame `raw` issues ~6,400 remote
invocations per second; the buffer libraries issue ~126, because a frame's worth of packets
becomes one call. Server to client, `raw` delivered roughly a sixth of what it was given while
the batching libraries delivered everything at the same payload size.

## Allocation per packet

`n` is how many sample windows survived the collector, out of 25 (encode) or the number of
500-packet windows in the run (decode).

| Cell | Encode B/call | n | Decode B/packet | n |
|---|---|---|---|---|
| Blink `ArrayHeavy` | 4487.7 | 4 | 641.0 | 295 |
| Zap `ArrayHeavy` | 3932.2 | 4 | **1474.6** | 148 |
| ByteNet `ArrayHeavy` | 3637.8 | 6 | **389.1** | 249 |
| raw `ArrayHeavy` | — | 0 | 641.0 | 53 |
| Blink `FlagIdiomatic` | 92.2 | 7 | 880.6 | 462 |
| Zap `FlagIdiomatic` | 81.9 | 5 | 573.4 | 549 |
| ByteNet `FlagIdiomatic` | — | 0 | 593.9 | 560 |
| raw `FlagIdiomatic` | — | 0 | 561.2 | 427 |
| Blink `FlagNaive` | 176.6 | 8 | 593.9 | 575 |
| Zap `FlagNaive` | 81.9 | 5 | 573.4 | 620 |
| ByteNet `FlagNaive` | — | 0 | 593.9 | 571 |
| raw `FlagNaive` | — | 0 | 561.2 | 444 |

**ByteNet allocates the least on decode, and the reason is one line.** Its `struct.read` does
`table.clone(input)`, so the result table starts with the schema's exact key set already sized;
Blink emits `local Value = {} :: any` and Zap emits `value = {  }`, and both then rehash as
keys are assigned. RESEARCH §3.8-S proposed exactly this trick for netweave from reading the
code — this run measures it, and shows the runtime-schema library beating both code generators
by 1.6x and 3.8x on the array payload.

Encode allocation for `raw` and for ByteNet's flag cells is missing, not zero: every window was
disturbed by a collection. Those cells need a smaller window or more repeats.

## What this fixes about the plan

- PLAN-M0 D-4 (bytes derived from `Stats`) was wrong and is replaced by `WireTap`. The first
  run reported 3.97 B for a 601 B payload; `Stats` does not account for buffer payloads in
  Studio, though it measures raw table traffic correctly.
- PLAN-M0 D-5 kept Blink's 1000 packets per frame. Studio runs uncapped at 200-240 FPS, so that
  is ~138 MB/s of offered load on `ArrayHeavy` and measures the send queue. Lowered to 200.
- PLAN-M0 D-3 assumed the collector could be stopped. It cannot; windowed medians replaced it.
